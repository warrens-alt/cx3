# ConversionX engineering audit — 21 September 2026

## Decision summary

The maintained application is a coherent, testable candidate for a controlled deployment, but this audit does **not** certify the production warehouse, source completeness, financial correctness, cloud configuration or a live deployment. The evidence-reporting path is deliberately stronger than the legacy exploration path: it requires a published immutable release, versioned definitions, independent checks and replayable evidence. Legacy routes remain visibly labelled `LEGACY_UNVERIFIED`.

The starting point was clean `main` at `7285e7a4b9ae2a6e7c3008bbfc40cd6920691639`, with successful GitHub Actions run `35623890394`. Before changes, type-check, 286 tests, build, Dataform compilation and 486 synthetic browser assertions passed. The initial dependency audit reported 11 known advisories: six high and five moderate.

The audited worktree now passes:

- locked install with 265 installed packages, reduced from 370;
- application and verification-tool `npm audit`: zero known vulnerabilities;
- TypeScript check using explicit React/React DOM definitions;
- 291 unit, contract and HTTP tests;
- production Vite and Express bundle;
- 491 Playwright assertions at desktop and mobile widths using handwritten synthetic API responses;
- Dataform compilation of 10 models and 20 assertions, plus publication-dependency graph checks.

The browser plugin was unavailable, so the repository's pinned Playwright 1.55.1/Chromium workflow was used as prescribed by the frontend testing procedure. Passing fixture tests do not establish live warehouse accuracy.

## Architecture and correctness assessment

The runtime is a React 19/Vite SPA with lazy route chunks, TanStack Query cancellation/cache identity, an Express 5 API boundary and BigQuery repositories. Signed IAP assertions and an explicit email/domain-to-tenant policy are verified server-side; unsigned user headers are not trusted. Tenant names and physical tables are configuration-owned, not caller-provided SQL identifiers. Dates, filters, operators, pagination, dimensions and metrics are allowlisted and values are bound as query parameters. Each BigQuery query has a maximum bytes-billed control. The API denies arbitrary table browsing.

The evidence-reporting path separates six fact grains and twelve metric definitions. It binds executions to tenant, subject, release manifest, engine source hash, cutoff, model/metric versions and immutable snapshot identities. Counts and amounts remain decimal strings. Ratios aggregate numerators/denominators rather than percentages. Evidence replay rechecks current permission and manifest identity. Missing or partial sources do not become zero.

The legacy path is useful for exploration but is not an independently reconciled reporting system. Its endpoints query a semantic layer over configured physical sources and return `NOT_VERIFIED` metadata. That boundary is visible in the UI and `X-Analytics-Status`. Corrected labels do not turn the underlying live joins into certified facts.

Detailed route/API/query coverage is in `docs/SURFACE-COVERAGE.md`; physical source and metric lineage is in `docs/SOURCE-METRIC-COVERAGE.md`.

## Performance and UX evidence

- The final production build contains 2,392 transformed modules. The initial application chunk is 311.16 KB raw / 97.98 KB gzip. The heaviest shared chart chunk is 372.75 KB raw / 109.86 KB gzip. Route screens and most chart modules are split into lazy chunks.
- Removing unreachable pages reduced the main generated stylesheet from 84.86 KB raw / 16.01 KB gzip to 76.87 KB / 14.70 KB gzip.
- The browser optimisation flow loads a 1,000-row synthetic breakdown but initially renders 25 rows, supports an explicit 50-row page, performs no additional analytical request during local search/sort/paging, and exports all 1,000 received rows. This was checked at 1440×1000 and 390×844.
- Desktop/mobile checks cover keyboard focus restoration and navigation trapping, no document-level horizontal overflow, reduced motion, exact/null/zero number handling, error/retry/cancel states, local-only filters, CSV/JSON export boundaries, and no page runtime errors.
- This is deterministic functional/performance evidence, not a production latency, Core Web Vitals or warehouse-cost benchmark. A live environment and representative network/data volumes are required for those measurements.

## Security and privacy boundary

Implemented: verified identity, explicit tenant grants, admin-only diagnostics, parameterised values, configured table allowlists, request/body/range limits, per-query byte budgets, in-process concurrency limits, same-origin protection, strict production browser headers, exact export limits, CSV formula neutralisation, principal-scoped caches, correlation IDs and structured audit records.

Still deployment-owned: HTTPS/IAP enforcement, exact production origins, service-account least privilege, central rate/quota enforcement across instances, durable log retention/alerting, WAF/edge rules, key rotation, data retention/deletion policy, incident response, backup/restore and penetration testing. The application does not send application data to an AI provider; the AI explanation endpoint returns an explicit unsupported response.

## Data and migration boundary

No production warehouse write, migration, snapshot, canonical ingestion or release publication occurred. The Dataform graph compiled; SQL was not executed in BigQuery. Warehouse bootstrap/publish commands remain preview-only unless an operator supplies `--execute`. The reference source contract remains `DRAFT`.

The failed read-only source check means actual schemas, types, regions, row counts, watermarks, uniqueness, join cardinality, source timezone, vendor coverage and commercial reconciliation remain unverified. A successful future run of `npm run sources:check` establishes read/query evidence only; source-owner approval and an independently reconciled published release are still required.

## Rollback

The application changes are source-only and no warehouse state was changed. Rollback is a normal Git revert of the audit commits, followed by the same locked install/verify/Dataform/browser workflow. Deleted repository artifacts remain recoverable from Git history. Do not roll a deployment back to a dependency graph with known advisories without separately addressing those advisories. No database rollback is required for this change set.

## Release recommendation

Suitable now: merge and retain as a tested source candidate.

Not yet defensible: “deployed”, “production-ready”, “live data verified”, “financially reconciled” or “all metrics accurate”. Before production acceptance, resolve DATA-01 and OPS-01, execute the synthetic warehouse reference in an isolated test project, obtain source-owner/contracts approval, publish a validated snapshot release, test real IAP acceptance and origin configuration, run representative performance/cost measurements, and verify the deployed commit SHA and health/observability path.
